Web search vs one API call on companies nobody has heard of

Bosco Labs · 22 November 2026

Counterparty-check benchmark 2. Pre-registered 2026-11-19, run 2026-11-20 and 2026-11-22, published 2026-11-22.

Bosco Labs designed this test, ran it, and sells one of the two things it compares. So that you do not have to take the result on trust, the rules, the scripts and the scoring were frozen and made public before the companies were drawn, the companies were drawn by a public random beacon, and every run's answers are published in the public repository (without the model's full text), with the script that turns them into these numbers.

On these companies the model reading counterparty-check reached the right decision more often than the model with web search. Across the three groups of companies, the model that made one call to counterparty-check reached the right decision in 100.0% of runs, and the same model with web search in 72.8%: a difference of +27.2 points (95% interval +19.4 to +35.0 points). Both replicates, run on different days, pointed the same way.

Most of that gap is in web runs where a web search or fetch returned an error (159 of the 204 web runs had at least one, most often the tool rejecting the model's input). Leaving those runs out, as a check named in advance does, the 31 companies that keep a run score 97.9% for web search and 100.0% for the API: +2.1 points (plus or minus 2 standard errors: -2.1 to +6.2 points), a gap this study cannot tell from zero. So the result mostly says that web search often did not get the register's answer for these companies, not that a model which got it read it wrong.

This holds for four registers (UK, Ireland, Latvia, Estonia), one model, and lookups where the right registration number was given. The answer key is read from the same registers the product reads, so the API's score measures whether it retrieves the official record, not whether the record is right. Read "What this does not show" before you rely on it.

Try the same call on your own suppliers: get a free $5 key (no card, about 100 company checks). It covers European registers (UK, Ireland, Norway, Sweden, Belgium, France and more); not US state registers.

The question

A buyer is about to pay a supplier it has never heard of. It has the supplier's legal name, country and registration number, and asks three things: is the company on the register and alive; is it in liquidation or an insolvency procedure; is it on the UK, EU or OFAC SDN sanctions list?

We gave the same question to the same model (Claude Sonnet 5.5, medium effort) in two ways:

  • Web: web search and web fetch, at most 6 searches and 6 fetches, 10,000 tokens per page. The question names the official register and gives its public by-number links, which makes this arm stronger than an agent that has to find the register itself, where the fetch tool can open those links. In Ireland it mostly could not: the fetch tool refused the Irish register's links in 42 of the 52 Irish web runs, and web search scored 30% there against 88 to 90% in the other three countries.
  • API: one call to counterparty-check with the registration number and country; the model answers from the result.

Two controls ran beside them: Memory (no tools: does the model already know these companies?) and Rule (the API's own pass / fail verdicts turned into answers by a fixed table, no model: does the model's reading help or hurt?). Every arm was told to answer "unknown" where its sources do not settle a field.

"Group A without sanctions" matters. For a sanctions list there is no page per registration number, so the web arm has to prove a negative ("not sanctioned") by searching the lists by name, while the API arm receives a ready sanctions verdict. That is the job the product is sold for, but it is a built-in advantage. This check scores group A on register status and insolvency alone, so you can see how much of the headline rests on the sanctions answer.

Excluded after the runs (register facts changed between the two reads, or the hand check disagreed): 0 of 90 companies in groups A, B and C. Above 10% the verdict would have been "no difference shown" whatever the intervals said (limit not exceeded).

What we cover, and what this test covers

Say it before anyone tests it: the version of counterparty-check frozen for this study reads 13 national company registers (plus a Spanish gazette index, which is not a register). This benchmark tests four of the registers. The frozen protocol says "nine": it was written on 2026-11-11, four registers (Lithuania, Slovakia, Belgium, Sweden) were added to the product between 16 and 18 November, and the protocol was not updated before the freeze. That number in it is out of date; the protocol itself is not changed after the freeze.

Left out: Poland, the Czech Republic, Norway, Finland and France. The check can look up one company there by number, but our code cannot list every company in those registers, and for Poland and the Czech Republic guessing numbers would break the registers' terms. The only way to include them would have been to pick companies by hand, which is the flaw of our first benchmark. So they are out.

Also left out: Lithuania, Slovakia, Belgium and Sweden (registers), and Spain (our gazette index, not a register). They were added to the product after the protocol was written, and the protocol was not reopened to include them.

This result says nothing about any of these nine registers or about Spain. Countries without a register of their own in the check were not tested either.

Sanctions: the UK Sanctions List, the EU consolidated list and the OFAC SDN list, matched on the company itself (not owners or officers).

How it was run

Full protocol: PROTOCOL.md. In short:

  1. Frozen first. The protocol, the scripts, the mapping from raw register values to answers, the prompts, the prices, the group size (30) and the verdict sentences were committed and published on 2026-11-19 in the public repository Bosco-Labs/bosco-labs-data, commit af7843e, folder benchmark2/prereg/. Bundle hash 8e07275e0d1a289e69624bea86e34653f23640fb7369efa1491563a91d193c68.
  2. Drawn by a beacon. The seed is sha256(bundle hash + ":" + randomness) of drand quicknet round 34127812 (2026-11-20 15:00 UTC), which did not exist when the bundle was published. Every eligible private limited company got a key from the seed (in the UK, every company incorporated on dates chosen by the seed); the smallest keys were taken. Skips only for reasons on a fixed list, all logged. The 200 smallest keys per cell are published with what happened to each (drawn, skipped and why, or not reached).
  3. Answer key from the registers, read by a script that shares no code with the product, twice (at the draw and after the last run); a person checked 12 rows chosen by hash and every group S row against the official page: 0 disagreements.
  4. Two replicates of web and API on different days, at least 20 hours apart; memory once. Set hash b38d0175742210c29509ac71e837c94b4a9ed54c77d517091f2d0db20a95fb3f published 2026-11-20 at 15:47 UTC in commit 8042fa9 (the set was drawn at 15:10 UTC; the first run began at 15:51 UTC), before any run; after each replicate the line count and SHA-256 of the full run journal were published (replicate 1, replicate 2). The full journal holds the model's text and is not published: runs_public.jsonl has the same attempt lines without it, so the counts can be checked but the journal hash cannot.
  5. No change to counterparty-check was deployed between the freeze and the last run. The API is one service, so three deploys for other tools (wallet-screening prices, x402 listing texts) restarted it; each is in the change log, with our statement that counterparty-check's code, price and texts were unchanged against the frozen commit (checked before each merge). Bugs found during the runs are listed as found, not fixed for this study: none found.

What this does not show

  • Four of the 13 registers, one model at one effort level, one set of tool limits. A different model or a purpose-built agent could score differently.
  • We built the product, wrote the protocol and ran the study.
  • The answer key comes from the same registers the product reads. This measures whether each arm retrieves the official record, not whether the record is right.
  • The correct registration number was always given. Name-only lookups, wrong numbers, owners, officers, VAT and bank details were not tested.
  • Ambiguous companies were skipped, so the set is easier than real life. Companies whose name is on a sanctions list without a number match were skipped too (none): those are the cases where a name screen raises a false alarm, so that skip can only help the API arm.
  • Groups are never pooled into one "accuracy": problem companies are two thirds of this set and a few percent of real suppliers.
  • Per-country and group S figures are small and descriptive only.
  • What you cannot check: that we did not try the product on the set between the draw and the runs or deploy a change to it, that no earlier freeze or draw was thrown away, and that no last run of a sitting was deleted from the journal before its count was posted. The public timestamps narrow this; only an outside party running the study would remove it.

Check it, or rerun it

Everything is in the public repository: the set with the truth and its official URLs, the skip log, the hand check, the per-run answers without the model's full text, the costs, the report, the pilot, and the change log: benchmark2/results.

From a checkout of Bosco-Labs/bosco-labs-data, with Python 3.12 and nothing else (use python3 if that is your Python 3.12 command):

cd benchmark2/prereg
python tools/bench2_prereg.py verify
python tools/bench2_analyze.py --dry-run --journal ../results/runs_public.jsonl --set ../results/set.json --audit ../results/audit.json --truth2 ../results/truth2.json

The first command checks every frozen file against the bundle hash; the second recomputes this page's numbers from the published runs and refuses if the run files do not match the pre-registration. The beacon's randomness for round 34127812 is public at https://api.drand.sh/52db9ba70e0cc0f6eaf7803dd07447a1f5477735fd3f661792ba94600c84e971/public/34127812, so the seed recomputes.
